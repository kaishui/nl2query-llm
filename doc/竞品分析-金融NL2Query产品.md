# 金融 NL2Query 产品竞品分析

> 目标：构建一个金融领域的 NL2Query（自然语言取数）产品，采用 **Cube.js 作为语义层**。
> 本文梳理市面竞品、给出对比维度，并论证 Cube.js 语义层路线的定位。

---

## 一、竞品全景（四类）

| 类别 | 代表产品 | 本质 | 与我们的差异 |
|---|---|---|---|
| **① 金融数据服务商** | 恒生聚源 AIDB / 综合问数 MCP、Wind、iFinD、同花顺问财 | 自带权威金融数据 + 指标三元组，走 NL2API/NL2SQL，端到端准确率宣称 95%+ | 它们卖「数据 + 取数」，我们卖「语义层能力」，不冲突，甚至可作为它们的数据上游 |
| **② 语义层 / Headless BI** | Cube.js、dbt Semantic Layer、AtScale、GoodData、Querio | 指标定义即代码，一处定义多接口消费，口径一致 | **我们选的路，直接竞品** |
| **③ AI 原生取数 Agent** | Aloudata Agent、AlphaSense Financial Data、BlazeSQL、Sequel AI | NoETL 明细语义层 + 多 Agent 协同，主打口径可控 + 归因/报告 | 偏「成品 Agent」，我们偏「可嵌入的语义底座」 |
| **④ 大厂云原生** | Snowflake Cortex Analyst、Databricks AI/BI Genie、BigQuery Gemini、Looker LookML | 仓库内语义视图，治理内建但锁定单一平台 | 无法跨仓，金融多数据源场景不适用 |

## 二、核心对比维度

### A. 语义层能力（技术底座）

1. **建模方式** — 代码即配置（Cube JS/YAML、dbt YAML）vs 可视化拖拽（LookML、AtScale）vs 无建模（裸 Text2SQL）
2. **查询接口覆盖** — SQL / REST / GraphQL / MCP / Python（Cube 最全，含原生 MCP server）
3. **确定性 SQL 编译** — 是否由语义层编译而非 LLM 直写 SQL（准确率的分水岭）
4. **口径一致性保障** — 一处定义、多端复用、指标漂移监控
5. **缓存与性能** — pre-aggregation 预聚合、两层缓存、秒级返回（Cube 强项）
6. **开源与可移植** — Apache 2.0、无厂商锁定（Cube / dbt 优于 LookML / Power BI）

### B. 金融 NL2Query 产品力（业务层）

7. **金融指标域知识** — 复权、除权、股本变动、季报披露滞后等口径处理（数据服务商最强）
8. **取数准确率** — 端到端准确率（恒生宣称 96%、Snowflake 语义模型下 90%+）
9. **多租户与行级安全** — 客户隔离、数据权限下钻到终端用户（Cube 原生支持）
10. **归因 / 分析增强** — 归因分析、自动解读、报告生成（Aloudata/AlphaSense 强）
11. **可嵌入性** — 能否嵌入自己的产品/App（Cube 的 headless 核心优势）
12. **数据源覆盖** — 是否跨仓、跨库（金融常需行情库 + 财务库 + 自建库联合）

## 四、为什么 Cube.js 适合做语义层

1. **开源核心（Apache 2.0）+ 无锁定** — 金融客户对供应商锁定和源码可控极敏感，自建部署可过合规。
2. **原生 MCP Server** — 让 LLM/Agent 通过受治理的指标取数，而非直写裸 SQL，这是「准确率」的结构性解法。
3. **确定性 SQL + 指标即代码** — 一个指标只定义一次，所有消费端（BI、App、Agent）口径一致，杜绝「两个分析师算出两个营收」。
4. **多租户 + 行级安全内建** — 客户嵌入场景（对外交付分析能力）的关键，天然支持。
5. **预聚合缓存** — 金融大表（逐笔、日频行情）秒级查询，省仓库算力成本。
6. **SQL/REST/GraphQL 全接口** — 下游无论接什么前端、BI 还是 Agent 都通吃。

### 代价 / 注意点

- Cube 是「工程框架」不是「成品」，金融指标口径（复权、行业分类、时间序列对齐）需要我们在 measure/dimension 层沉淀。
- 这块才是我们与数据服务商拉开差距的核心资产，也是最重的工程投入。
- 无内置可视化，需要自己搭前端或接第三方 BI。

## 五、产品定位建议

**差异化定位**：以 Cube.js 语义层为核心，叠加**金融指标口径库**（复权、行业、财年对齐等），做「可嵌入的金融语义层底座」。

**三条可选路线**：

| 路线 | 目标客户 | 关键优势 | 主要投入 |
|---|---|---|---|
| **A. 内部 BI 问数** | 金融机构内部 | 快速落地、口径统一 | 低 |
| **B. 对外嵌入交付（SaaS）** | 券商/资管/财富 App | 多租户、可嵌入是刚需 | 中 |
| **C. 金融语义层中间件** | 数据服务商、Agent 厂商 | 成为上游底座 | 高（指标库沉淀） |

**推荐**：B 路线最契合 Cube 的核心优势（headless + 多租户 + RLS + 嵌入），也是 ①③④ 类竞品最弱的一环。
