# 银行 NII 智能问数系统 · 技术架构方案

> 基于 Cube.js 语义层 + LLM/MCP 的自然语言 NII 归因分析系统。
> 场景：某银行内部 NII 明细数据，对内投研/分析工具，单机构深钻分析。

---

## 一、定位与优劣势分析

### 1.1 定位

本系统不是「通用金融 NL2Query」（那需要与恒生聚源 AIDB、Kensho 等数据服务商竞争），而是 **「单机构私有 NII 数据的智能问数 + 归因分析助手」**。

| 维度 | 通用金融 NL2Query | 本系统（NII 深钻） |
|---|---|---|
| 数据 | 公开市场数据 | 私有 NII 明细 |
| 竞品 | 恒生聚源 AIDB、Kensho | **无直接竞品**（私有数据不可复制） |
| 壁垒 | 数据权威性 | 私有明细 + 口径 + 归因逻辑 |
| 核心价值 | 跨机构对比 | NII 驱动因子归因分析 |

### 1.2 优势

1. **数据不可复制** — NII 内部明细是竞品拿不到的私有资产，天然护城河。
2. **Cube.js 完美契合** — 单机构 + 私有数据 + 自托管，Cube 的 headless、确定性 SQL、指标即代码、预聚合全部用得上，且开源可控过银行合规。
3. **口径即代码** — NII、NIM、生息资产收益率等口径沉淀为版本化的 cube 定义，杜绝「两个分析师算出两个 NIM」。
4. **无厂商锁定** — Apache 2.0 自部署，数据不出行内，满足金融监管与审计要求。
5. **LLM 直写 SQL 的根治方案** — 通过 MCP 让 LLM 从「受治理指标」取数，而非直写裸 SQL，从结构上消除幻觉与口径漂移。

### 1.3 劣势与风险

1. **建模成本前置** — 必须先有人把 NII 口径、维度、归因逻辑定义清楚，Cube 才「有用」。前期是纯投入，无产出。
2. **归因逻辑复杂** — NII 的规模/价格/结构分解不是简单聚合，需要在语义层额外实现，是最大的工程难点。
3. **数据质量依赖** — 若明细数据口径不统一（不同分行/产品粒度不一致），建模前必须先治理。
4. **Cube 无内置可视化** — 前端（Chat + 瀑布图）需自研或接第三方。
5. **LLM 幻觉仍需兜底** — 语义层能消除「取数口径」幻觉，但「归因解读」仍可能出错，需要来源可追溯 + 结果校验。

## 二、技术架构

采用四层架构：**交互层 → Agent 编排层 → 语义层（Cube.js）→ 数据层**。

### 2.1 交互层 · 问数前端

- **自然语言问数 Chat**：分析师用自然语言提问，如「Q3 NII 环比下降的原因是什么」。
- **归因分析可视化**：瀑布图展示规模效应 / 价格效应 / 结构效应的贡献分解。
- 技术选型：React / Next.js + 图表库（ECharts / Recharts）。

### 2.2 Agent 编排层 · LLM + 取数

- **意图识别**：区分「问数 / 归因 / 预测」三类意图，归因类触发澄清式反问（如「是环比还是同比？」「看哪个分行？」）。
- **MCP Client**：通过 Model Context Protocol 调用 Cube 的受治理指标，组合多步查询。
- **结果解读**：基于取数结果生成归因结论，结论附来源指标，可追溯。

### 2.3 语义层 · Cube.js（核心）

- **NII 指标口径库**：NII / NIM / 生息资产余额 / 生息资产收益率 / 计息负债成本率，以及规模效应 / 价格效应 / 结构效应归因指标，全部定义为 cube。
- **能力输出**：MCP Server / SQL / REST / GraphQL 四接口，供 Agent 与前端消费。
- **确定性 SQL 编译**：由 Cube 编译 SQL，而非 LLM 直写，保证口径一致。
- **预聚合缓存**：金融大表秒级查询，省算力。
- **多租户 / 行级安全**：按分行/部门/角色隔离数据。

### 2.4 数据层 · 私有 NII 明细

- **NII 明细宽表**：按日/月 × 分行 × 产品线，含利息收入、利息支出、生息资产余额、计息负债余额、利率。
- **口径字典 / 元数据**：指标定义、别名、单位、财年对齐、复权口径。
- **湖仓 / 数据仓库**：DuckDB（PoC）/ Postgres / ClickHouse（生产），离线批处理 + 增量同步。

## 三、NII 归因分析建模（核心难点）

NII 归因本质是「量 × 价」分解：

```
NII = Σ(生息资产余额 × 生息资产收益率) - Σ(计息负债余额 × 计息负债成本率)
    = 资产端利息收入 - 负债端利息支出
```

**归因三效应**（环比/同比增量分解）：

| 效应 | 含义 | 计算逻辑 |
|---|---|---|
| 规模效应 | 余额变化贡献 | Δ余额 × 上期利率 |
| 价格效应 | 利率/收益率变化贡献 | 上期余额 × Δ利率 |
| 结构效应 | 资产/负债结构变化贡献 | 交叉项（残差） |

这三类效应需在 Cube 语义层用 `measures` 定义，供归因分析直接查询。

## 四、关键技术选型

| 组件 | 选型 | 理由 |
|---|---|---|
| 语义层 | Cube.js（Core，Apache 2.0） | 开源自托管、指标即代码、MCP、预聚合 |
| LLM 接入 | MCP Server（Cube 原生） | 受治理取数，消除口径幻觉 |
| 存储（PoC） | DuckDB / SQLite | 零运维，单机快速验证 |
| 存储（生产） | Postgres / ClickHouse | 行级安全 + 分析性能 |
| 前端 | React + ECharts | 问数 Chat + 瀑布图 |
| 编排（可选） | 轻量 Agent 框架 | 意图识别 + 多步查询编排 |

---

## 五、落地路径（四步）

1. **数据摸底** — 梳理 NII 明细的表结构、字段、粒度，明确口径。
2. **Cube 语义建模** — 把 NII 指标 + 归因三效应写成 cube schema。
3. **接 LLM + MCP** — 跑通「自然语言 → 受治理指标 → SQL → 结果」链路。
4. **前端 + 归因可视化** — 问数界面 + 瀑布图，端到端可用。

---

## 六、已知限制与后续

- 归因三效应（尤其结构效应交叉项）的精确分解，需结合具体数据粒度在实现阶段细化。
- LLM 归因解读需引入「来源指标 + 数值校验」兜底，避免解读幻觉。
- 预测类问数（未来 NII 走势）需额外引入时序模型，当前架构聚焦「问数 + 归因」。
