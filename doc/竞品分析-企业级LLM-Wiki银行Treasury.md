> 文档日期：2026-11-07

> 关联仓库：github.com:kaishui/nl2query-llm（本仓库 doc/ 目录沉淀）

## 一、先厘清一个概念：你做的「LLM Wiki」到底指哪一类？

调研发现，行业里「LLM Wiki」一词有两个截然不同的内涵，选型前必须先对齐，否则竞品范围、技术栈、成本预算全都会跑偏：

| 维度 | A. Karpathy 式「编译型 LLM Wiki」 | B. 企业级「AI 知识库/RAG 平台」 |
|------|-----------------------------------|-------------------------------|
| 核心理念 | LLM 作为「编译器」，把 raw 材料编译成**结构化 Markdown wiki**，知识沉淀在文本里 | LLM 作为「检索 + 生成引擎」，知识沉淀在**向量索引**里，查询时实时召回 |
| 检索方式 | index.md + 摘要 + 反向链接导航，**无向量库** | 向量检索 + 关键词混合 + 重排 |
| 知识形态 | 人可读的 Markdown（概念页/实体页/对比页） | 文档分块（chunk）+ embedding |
| 规模上限 | 约数百页 / 100K–1M 词（个人～部门级） | 数十万～数百万文档（企业级） |
| 更新成本 | LLM 增量重编译，Token 省 84–95% | 重新分块 + re-embedding |
| 可解释性 | 高（明文可读、可 diff） | 中（向量黑盒，靠引用回源） |
| 权限/ACL | 无内建，需自己实现 | 平台内建 |
| 典型代表 | Karpathy 个人工作流、Obsidian + Claude Code | Notion AI、Glean、腾讯乐享、Dify、FastGPT |

**关键结论（对你的场景）：**
银行 Treasury 是强监管、强合规、强审计的环境，**纯 A 方案（无 ACL、无审计、无权限）直接上企业场景会被合规一票否决**（Atlan 调研结论：个人 wiki 到企业级是「最残酷的跳跃」，核心矛盾是数据治理而非检索架构）。但 A 方案的**「编译沉淀 + 人可读 + 可版本化」**思想，恰恰是银行最需要的「知识治理」能力。

因此本方案定位为 **「A 的思想 + B 的工程能力」的混合架构**：以受治理的 Markdown/wiki 作为**高置信知识层（curated anchor）**，以 RAG 作为**海量文档检索层（broad retrieval）**，两层协同。这与贵司 nl2query-llm 现有「受治理指标口径 + LLM 只做意图识别」的架构哲学一脉相承。

## 二、竞品分析：分三个赛道看

银行 treasury 的 LLM Wiki，竞品不是单一一类，而是横跨三个赛道，每个赛道对你有不同的借鉴价值和竞争压力。

### 赛道 1：AI 原生企业知识库（直接竞品）

| 产品 | 定位 | 核心能力 | 银行 treasury 相关度 | 关键不足 |
|------|------|----------|---------------------|---------|
| **Glean** | 企业级工作场所搜索 + AI 问答 | 权限感知索引、跨系统连接（Drive/Slack/Jira/Confluence）、企业搜索最强 | ★★★★ 高（企业搜索标杆） | 偏文档搜索，不查实时业务数据；企业版昂贵；国内部署受限 |
| **Notion AI** | AI 工作空间 | 文档 + 数据库 + AI 问答 + 自定义 Agent | ★★★ 中（偏协作） | 只查 Notion 内内容；无实时业务数据；企业级权限/安全弱 |
| **腾讯乐享** | 腾讯系 AI 原生知识库 | Agentic 设计、多格式解析、AI 自动结构化、四级权限隔离、多模态生成 | ★★★★ 高（国产合规首选） | 绑定腾讯生态；深度定制受限 |
| **ima / 语雀** | 个人/团队知识库 | 剪藏、中文原生、轻量 | ★★ 低 | 非企业级，无审计 |
| **Confluence + AI** | Atlassian 研发文档中心 | 与 Jira 打通、层级页面、企业权限 | ★★★ 中 | 偏研发协作，非金融知识治理 |

### 赛道 2：开源 RAG / 智能体平台（技术底座候选）

| 产品 | 定位 | 核心能力 | 对你的价值 | 权衡 |
|------|------|----------|-----------|------|
| **Dify** | 开源 LLM 应用平台 | 可视化工作流、混合检索 + 重排、多模型、Agent、本地/混合部署 | ★★★★★ 可直接做 PoC 底座 | 需自建治理/审计层；金融合规仍需自己补 |
| **FastGPT** | 零代码知识问答 | 拖拽式、多格式结构化、多轮对话、Docker 便捷 | ★★★★ 快速落地 | 深度定制能力弱于 Dify |
| **RAGFlow** | 深度文档理解 RAG | 版面分析、复杂表格解析、引用溯源强 | ★★★★ 金融文档友好 | 相对新，生态略小 |
| **Qdrant / Weaviate / Milvus** | 向量数据库 | 底层向量检索 | ★★★ 组件而非产品 | 需自己搭 pipeline |
| **LangChain / LlamaIndex** | 智能体框架 | 编排层 | ★★★★★ 与现有 LangChain 栈一致 | 非产品，是零件 |

> **对你的直接启示**：既然 nl2query-llm 已经基于 LangChain 1.4 / LangGraph 1.2 构建，且强调「LLM 不直写 SQL、代码确定性拼装」的治理哲学，那么 LLM Wiki 的 PoC 最自然的路径是 **LangChain + LangGraph 编排 + 自建治理层**，而非直接采购 Notion AI 或 Glean。Dify 可作为快速原型对照，验证检索质量后再决定是否自研。

### 赛道 3：LLM Wiki 方法论工具（思想来源）

| 工具 | 作用 | 借鉴点 |
|------|------|--------|
| **Karpathy LLM Wiki 工作流** | raw/ 目录 → LLM 编译 → 结构化 wiki → lint 维护 | 三层架构、ingest/query/lint 三操作、index.md + log.md、增量编译、Token 省 84–95% |
| **OKF（Open Knowledge Format）** | Google 开放知识格式 | Wiki 页 = YAML 元数据 + Markdown，作为知识交换标准 |
| **GraphRAG** | 图检索 | wiki 反向链接本质是「手写版 GraphRAG」，可升级为知识图谱 |
| **Obsidian** | 浏览前端 | 双向链接、图视图，作为「wiki 的 IDE」 |

## 三、竞品分析应包含的核心维度（方法论）

这是你问的重点——「竞品分析应该包含哪些维度」。以下维度框架可直接复用，也是本方案的评估矩阵：

### 3.1 功能维度
1. **知识接入**：支持的文件/数据源广度（PDF/Word/Excel/数据库/API/实时数据）
2. **知识加工**：自动解析、结构化、分块、摘要、实体抽取、去重
3. **检索能力**：关键词 + 向量混合检索、重排、引用溯源、跨文档聚合
4. **问答与生成**：多轮对话、Agent 编排、多模态输出（表格/图表/报告/PPT）
5. **知识治理**：版本管理、审核流、过期管理、知识所有者（ownership）

### 3.2 企业级维度（银行场景权重最高）
6. **权限与 ACL**：细粒度（组织-部门-库-单篇）、检索内嵌权限（非前端关卡）
7. **安全合规**：私有化部署、数据加密、等保/金融行业监管适配、审计日志
8. **可审计性**：每次答案可回源、检索日志、变更痕迹链（谁/何时/何源）
9. **可解释性**：答案是否附引用依据、是否支持「不确定/需人工确认」

### 3.3 技术维度
10. **架构范式**：RAG / LLM Wiki / GraphRAG / Agentic Search 的取舍与融合
11. **模型接入**：多模型、私有化模型（信创）、embedding 可控
12. **扩展性**：规模上限、增量更新成本、re-index 代价
13. **可观测**：全链路 trace、检索质量评估、幻觉监控

### 3.4 成本维度
14. **建设成本**：RAG 企业级初始 $15K–$40K，完整生产 $40K–$100K；LLM Wiki 仅 ~$500 初始
15. **运营成本**：RAG 月度 $8K–$19K vs LLM Wiki ~$50/月；Token 效率差 84–95%
16. **隐性成本**：数据清洗（占项目 30–50%）、分块调优、长期维护

### 3.5 生态与合规维度
17. **生态绑定**：与现有办公/研发/数据工具链的集成成本
18. **国产化/信创**：私有化模型、国产数据库适配
19. **监管适配**：MAS TRM、HKMA SPM、中国银保监（金监总局）AI 治理要求

## 四、银行 Treasury 场景的差异化需求（竞品都做不好、你必须做好的）

这是「为什么银行不能直接用 Notion AI / Glean」的答案，也是你的产品护城河：

| 需求 | 说明 | 通用竞品的短板 |
|------|------|---------------|
| **术语库与指标口径统一** | 银行资金条线「久期、DV01、FTP、LCR、NSFR、头寸、NII」等术语和指标口径必须唯一定义 | Notion/Glean 无领域口径治理 |
| **监管知识实时性** | 监管文（银保监、央行、MAS、HKMA、Basel）频繁更新，需「新鲜度治理」 | 通用库不区分内部/外部知识、无生效时间 |
| **ACL 检索内嵌** | 资金业务数据敏感，权限必须在检索层执行，而非前端遮罩 | 多数产品权限在应用层 |
| **可审计证据链** | 监管要求每次结论可回源（源、所有者、认证时间、范围） | 缺乏检索日志与变更痕迹 |
| **高风险话题拦截** | 投资建议、收益率承诺、风险评级等需明确回答边界 | 无金融合规话术校验 |
| **业务指标挂钩** | 与 NII、头寸等实时业务数据联动（问答可查数） | 通用库不连实时业务数据 |
| **归因/计算能力** | 规模/价格/结构归因等确定性计算 | 纯 RAG 只会检索，不会计算 |

> **与 nl2query-llm 的关系**：本 LLM Wiki 可作为 nl2query-llm 的「知识底座」。nl2query-llm 负责「问数」（受治理指标 + 确定性 SQL），LLM Wiki 负责「问知识」（术语口径、监管政策、操作规程）。两者共享同一套「指标口径字典」和「合规审批」体系，形成「知识 + 数据」的统一入口。

## 五、推荐建设方案（PoC 路线图）

### 5.1 总体架构（混合型）

```
┌─────────────────────────────────────────────────────────────┐
│                        接入层（统一入口）                      │
│        Web 问答界面 / API / 与 nl2query-llm 集成              │
└──────────────────────────┬──────────────────────────────────┘
                           ▼
┌─────────────────────────────────────────────────────────────┐
│                    编排层（LangGraph）                        │
│  意图识别 → 路由 → 检索/编译 → 校验 → 生成 → 审计            │
│  ├─ 知识问答（走 RAG / wiki 检索）                           │
│  ├─ 指标问答（走 nl2query 受治理口径）                        │
│  └─ 高风险查询 → interrupt 人工审批                           │
└──────────────┬──────────────────────────┬───────────────────┘
               ▼                          ▼
┌──────────────────────────┐  ┌───────────────────────────────┐
│  高置信知识层（LLM Wiki）  │  │   海量检索层（RAG）            │
│  · 受治理指标口径字典       │  │  · 监管文/制度/报告分块索引    │
│  · 术语库 / 操作规程        │  │  · 向量 + 关键词混合检索       │
│  · 结构化 Markdown + 版本  │  │  · 引用溯源                   │
│  · 人工审核 + ownership    │  │                               │
└──────────────────────────┘  └───────────────────────────────┘
               ▼
┌─────────────────────────────────────────────────────────────┐
│   治理与合规层（贯穿全链路）                                  │
│  · ACL 检索内嵌 · 审计日志 · 版本管理 · 新鲜度治理 · 高风险拦截 │
└─────────────────────────────────────────────────────────────┘
```

### 5.2 技术栈建议（与现有项目对齐）

| 层 | 推荐 | 理由 |
|----|------|------|
| 编排 | LangGraph（已用 1.2） | 复用现有状态图、interrupt 审批、Checkpointer |
| 检索 | 先轻量（SQLite FTS5 / 自研 index.md），后升级向量库 | PoC 阶段 LLM Wiki 模式够用，规模上来再接 Qdrant/Milvus |
| 知识存储 | Markdown + Git 版本管理（复用 doc/ 目录规范） | 可 diff、可审计、可回滚，天然满足证据链 |
| 模型 | 私有化/信创模型为主，embedding 自控 | 金融数据不出域 |
| 安全 | sql_guard 思路延伸到「知识检索 guard」 | 复用 nl2query 的只读白名单思想 |
| 前端 | 轻量 Web（可选 Obsidian 作内部浏览） | 快速验证 |

### 5.3 落地阶段（建议 3 步）

**Phase 1 — 术语与口径底座（1–2 周）**
- 盘点 treasury 条线核心术语 + 指标口径（复用 nl2query 的 metrics.py 口径）
- 落成结构化 Markdown「口径字典」+ index.md + 版本控制
- 产出：一个可 diff、可审计的受治理知识底座

**Phase 2 — LLM Wiki 编译与问答（2–4 周）**
- 接入 LangGraph，实现 ingest（增量编译）/ query（引用回源）/ lint（一致性检查）三操作
- 高风险话题拦截 + 人工审批 interrupt
- 产出：可运行 PoC，验证「编译沉淀 + 引用回源」在 treasury 场景的效果

**Phase 3 — RAG 扩展 + 合规加固（持续）**
- 海量监管文档接入向量检索（混合检索 + 重排）
- 补全 ACL 检索内嵌、审计日志、新鲜度治理、监管适配（金监总局 AI 治理 / MAS TRM / HKMA SPM）
- 产出：企业级可交付版本

## 六、关键风险与对策

| 风险 | 说明 | 对策 |
|------|------|------|
| **LLM Wiki 规模天花板** | 数百页以上导航失效、上下文溢出 | 规模上来切向量检索，wiki 作 curated 层 |
| **数据治理缺失** | 上游文档过期/无认证，两种方案都会失败 | 先建「源数据认证 + ownership + 新鲜度治理」 |
| **幻觉不可容忍** | 斯坦福研究：最优法律 RAG 仍有 ~17% 错误率 | 强制引用回源 + 高风险拦截 + 人工复核 |
| **多用户并发写冲突** | 多人同时改 Markdown 无事务支持 | 走 Git PR 审核流，或转数据库 |
| **合规违规** | 金融 AI 受 MAS/HKMA/金监总局监管 | 从 Day 1 内建审计、可解释性、人工审批 |
| **成本失控** | RAG 企业级初始 $34K–$58K | PoC 用 LLM Wiki 模式（~$500 起步），验证后再扩 |
