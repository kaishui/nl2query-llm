# 金融 NL2Query 竞品分析（聚焦版）

> 聚焦「金融领域的自然语言取数（NL2Query / NL2SQL / NL2API）」，而非宽泛的语义层 / BI / Agent 对比。
> 结论先行：**金融 NL2Query 的竞争壁垒不在语义层技术，而在「权威金融数据 + 指标口径」。**

---

## 一、核心认知：金融 NL2Query ≠ 通用 NL2SQL

| 维度 | 通用 NL2SQL（Cube / dbt / Cortex） | 金融 NL2Query（AIDB / Kensho / AlphaSense） |
|---|---|---|
| 解决的核心问题 | 语义层技术：一处定义、多端口径一致 | 数据权威性 + 指标口径：复权、行业分类、财年对齐 |
| 竞争壁垒 | 工程能力、开源、可移植 | 数据积累 + 领域知识（20 年金融数据） |
| 准确率瓶颈 | 建模质量 | 指标口径定义 + 数据治理 |
| 商业模式 | 卖框架 / SaaS | 卖数据 + 取数服务 |

**结论**：你选择 Cube.js 做语义层，只解决了「技术底座」，真正的差异化必须建立在**金融指标口径库**之上。否则会陷入与通用语义层产品（Cube 官方 Cloud、dbt SL）的同质竞争，打不赢恒生聚源 AIDB、Kensho 这类「数据 + 口径」玩家。

## 二、聚焦后的竞品地图（三类核心玩家）

### ① 金融数据底座派（直接竞品）

| 产品 | 数据来源 | 取数方式 | 准确率宣称 | 商业模式 | 关键特点 |
|---|---|---|---|---|---|
| **恒生聚源 AIDB** | 自有全市场数据（20 年） | NL2API / NL2SQL / MCP | NL2API >90%，端到端 >96% | 数据订阅 + 取数服务 | 「指标三元组」三表体系，SWOD 极简查询，2000+ 指标 |
| **恒生聚源综合问数 MCP** | 同上 | MCP（5 工具：通用问数/宏观/研报/股票筛选/基金筛选） | 稳定 95%+ | 按量计费，上架百炼 | 覆盖股票/债券/基金/宏观/财务，100+ 机构接入 |
| **Kensho（S&P Global）** | S&P 指数/评级/基本面 | NL-to-SQL + MCP | 高（S&P 数据权威） | 开发者 API | 自然语言生成复杂 SQL，MCP 协议领先 |

### ② 投研智能终端派（数据 + 工作流，偏「分析」而非「取数」）

| 产品 | 定位 | 核心能力 | 与你的差异 |
|---|---|---|---|
| **Bloomberg GPT（ASKB）** | 终端内对话式投研 | 500 亿参数 + 40 年数据，多 Agent 架构 | 数据壁垒无法复制，卖终端 |
| **AlphaSense Financial Data** | 定量 + 定性融合问数 | 结构化财务（Canalyst 4500 模型）+ 5 亿文档 | 卖「研究工作流」，非取数基础设施 |

### ③ 你（Cube.js 语义层路线）

- **定位**：可嵌入的金融语义层底座，不自带数据，但沉淀金融指标口径
- **差异点**：开源自部署（过合规）、多租户 RLS、headless 可嵌入、指标口径可控
- **需补的短板**：权威数据源 + 复权/行业/财年等口径处理

## 三、聚焦后的对比维度（收敛为 10 个）

原宽口径的 12 维度中，聚焦金融 NL2Query 后，**权重最高的前 5 个**：

### 核心维度（决定生死）

1. **数据权威性与覆盖** — 是否自带权威金融数据（AIDB/Kensho 完胜，Cube 路线需外接）
2. **指标口径正确性** — 复权、除权、股本变动、季报披露滞后、行业分类、财年对齐（金融特有，这是最大护城河）
3. **端到端取数准确率** — 从自然语言到最终数据的全链路准确率（AIDB 96% vs Snowflake 90%+）
4. **金融场景覆盖深度** — 股票/基金/债券/指数/宏观/财务/EDB 等品类覆盖
5. **金融术语理解** — 领域 NER、同义词（如「营收」=「营业收入」）、指标别名

### 支撑维度（技术能力）

6. **取数接口形态** — NL2SQL / NL2API / MCP / 直查（AIDB 的 SWOD、Kensho 的 MCP）
7. **确定性 SQL / 口径一致性** — 语义层编译 vs LLM 直写（Cube 的优势）
8. **多租户与行级安全** — 客户隔离、数据权限下钻（Cube 强项，AIDB 较弱）
9. **可嵌入性 / 开源可控** — 能否嵌入自己产品、源码可控过合规（Cube 强项，AIDB/Kensho 是黑盒）
10. **性能与成本** — 预聚合缓存、金融大表秒级查询、按量计费（Cube 预聚合 vs AIDB 数据订阅）

## 四、Cube.js 路线的差异化定位（关键结论）

**不要和 AIDB / Kensho 正面拼「数据 + 口径」，那是 20 年积累打不过的。**

正确的卡位是：

| 对手 | 它的弱点 | 你的机会 |
|---|---|---|
| 恒生聚源 AIDB | 黑盒、不开源、绑定其数据、多租户/嵌入弱 | 开源自部署、可嵌入、多租户 RLS、跨数据源 |
| Kensho | 绑定 S&P 数据、无自托管 | 源码可控、私有化部署过合规 |
| Cube Cloud / dbt SL | 无金融指标域知识 | 沉淀金融口径库，成为「金融语义层」 |
| Snowflake Cortex | 锁定 Snowflake、无金融口径 | 跨仓、金融场景定制 |

**一句话定位**：做「**金融行业专用的、可自托管可嵌入的语义层**」，用 Cube.js 承载金融指标口径（复权、行业、财年对齐），向下兼容任意数据源（行情库/财务库/自建库），向上对接 LLM/Agent（MCP）与自研前端。

**这是 AIDB/Kensho（黑盒数据服务）和 Cube/dbt（通用语义层）之间的空档。**

## 五、落地的关键问题（下一步要决策）

1. **数据源**：自建还是接恒生聚源/Wind/自研行情？（决定你是「数据服务商」还是「语义层中间件」）
2. **目标客户**：内部 BI、对外嵌入 SaaS，还是数据服务商/Agent 厂商的中间件？
3. **首个 PoC 指标**：选 3 个最能体现口径壁垒的指标（如「前复权收盘价」「行业归母净利润」「财年对齐营收」）
4. **准确率 benchmark**：建立金融问数评测集，对标 AIDB 的 96% 端到端准确率
